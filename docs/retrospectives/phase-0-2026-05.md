## 1. Pre-deploy user lifecycle audit

Conducted during pre-deploy DB state verification on 2026-05-19. Three findings 
related to user data governance surfaced from a single audit pass. None were 
ship-blockers but all required acknowledgement.

### Finding 1.1: Clerk publicMetadata.plan never actively written

**Observation**: Only 2 real Pro users exist in production user_usage (after orphan 
cleanup): user_3BN1HkLU7kw7458c351oqMVwmv9 (Andrew personal, only real Pro account). 
Manual Clerk Dashboard inspection of that user's publicMetadata confirmed no `plan` 
key has ever been written.

**Architectural implication**: The frontend `_app.tsx` PostHog identify() path reads 
`publicMetadata.plan` and forwards it as a person property. Since the field is 
never set, identify() always reads `undefined` and falls back. Backend gating uses 
user_usage.plan_type exclusively. This is a dormant dual-source pattern — no active 
drift today, but the TypeScript signature suggests an alternative source-of-truth 
that doesn't exist.

**Decision**: P2 TECH_DEBT entry filed. Phase 1A §3.1 scope will consolidate plan_type 
read paths to user_usage exclusively, dropping the publicMetadata.plan signature 
unless a real use case emerges.

## 3. OG image 404 — production fix-forward

### Symptom

During PART C deploy verification, LinkedIn Post Inspector showed share preview 
cards with title + domain but no image. Direct curl confirmed 
`https://vela.an-tho.com/static/og/<share_id>.png` returned 404 for both active 
and revoked shares, and `https://vela.an-tho.com/og-image.png` (landing page) also 
returned 404.

### Investigation

Driven by audit prompt to Claude Code at HEAD 0950157 (post-initial-v163-deploy). 
Investigation produced 6-hypothesis ranked report. Real root cause emerged 
mid-investigation as Hypothesis F (not in original brief):

**Hypothesis F (real root cause)**: The catch-all StaticFiles mount 
`app.mount("/", StaticFiles(directory="static"))` resolves URL `/static/og/<id>.png` 
to filesystem path `static/static/og/<id>.png` — i.e., double-prefixes "static/". 
The on-disk file at `static/og/<id>.png` was never reachable at the emitted URL.

**Hypothesis C (real, deferred)**: `/static/og/*` lives on Fly's ephemeral 
filesystem. No `[mounts]` section in fly.toml, no R2/CDN integration despite 
.gitignore comment promising one. Even after Hypothesis F is fixed, PNGs vanish 
on every machine restart, redeploy, or scale event.

### Fix scope (commit a63b304)

Surgical 12-LoC fix in api/server.py + 3 unit tests in tests/services/test_og_image.py:

1. **Dedicated mount above catch-all** (~7 LoC including mkdir): 
   `app.mount("/static/og", StaticFiles(directory="static/og"), name="og_images")` 
   registered before the catch-all so URL `/static/og/<id>.png` resolves correctly. 
   Comment in code explains the double-prefix gotcha to prevent future refactor 
   regression.

2. **Re-share idempotency hole plug** (~4 LoC): In `/api/share/create` endpoint's 
   "existing SharedQuery" early-return branch, call `_generate_og_png()` inside 
   try/except. Idempotent (og_image.py:160 skips if file exists), defensive against 
   the ephemeral-fs case where a previously-generated PNG was lost.

3. **Unit tests**: 3 cases covering (a) generate writes file, (b) generate idempotent 
   via mtime unchanged, (c) end-to-end `/static/og/<id>.png` 200 image/png via 
   TestClient. All 24/24 tests green (3 new + 21 existing providers).

### Verification post-v164

- `curl -I https://vela.an-tho.com/og-image.png` → 200 + image/png + 55KB
- `curl -I https://vela.an-tho.com/static/og/-1C8ZqfFOqg.png` (fresh share) → 200 
  + image/png + 20KB
- LinkedIn Post Inspector preview for `https://vela.an-tho.com/q/-1C8ZqfFOqg` 
  shows title + image + domain

### Ephemeral filesystem (Hypothesis C) — deferred

Acknowledged in commit message. Phase 1A entry decision: Fly volume mount (~5 LoC 
fly.toml, single-region, simpler) vs R2/CDN (more work, matches .gitignore comment 
intent, multi-region future-proof). Likely ADR-worthy decision; ADR number TBD 
(007 or 008 depending on other work).

### Lessons

- **No bot fetch verification during §4.5 dogfooding**. §4.5 PHASE A-D dogfooding 
  exercised share creation, page rendering, revoke flow, and PostHog events — but 
  no team member fetched the og:image URL or pasted a share URL into LinkedIn / 
  Twitter / Google validators. The bug was reachable by any social media bot but 
  never tested. **Add to §4.5+ feature work: external validator check as part of 
  PHASE D acceptance, not deferred to PHASE E production.**

- **Catch-all mount + dedicated mount ordering matters**. Anyone adding a static 
  serving path in the future needs to register it ABOVE the catch-all, not below. 
  Comment in api/server.py serves as canary.

## 4. Production deploy mechanics — what worked, what didn't

### What worked

- **CLAUDE.md Rule 6 production state ban**: Backend respected production-only 
  config (TEST_MODE inactive, real Clerk auth, real Dodo webhook secret). No 
  shortcut left in code.

- **Phase 0 dogfooding baseline transferred cleanly**: §2.7 canonical Furosemide 
  case in production matched §2.7 Step 8 acceptance protocol output 1:1 (3 items + 
  correlations + risk_tier + source chips). No regression from dev environment.

- **Two-cycle deploy framing**: Discovering OG image bug post-v163 didn't trigger 
  rollback. Fix-forward (a63b304 → v164) was clean and under 1 hour from discovery. 
  PART D.1 🟡 HIGH classification (not 🔴 CRITICAL) was the right call.

- **Pre-deploy state audit caught hidden cleanup**: Orphan row + Dodo sandbox 
  test_cust_ scan executed before deploy.ps1 ran. Cleaning before deploy meant 
  retrospective documents a clean baseline, not a contaminated one.

### What didn't work

- **deploy.ps1 hardcoded 10s settle**: Vector store load takes 30-60s on cold 
  machine. The 10s wait built into Step 2 of deploy.ps1 is insufficient. 
  Workaround: manual 60s sleep after deploy.ps1 exit before running B.3 smoke 
  curls. **P3 TECH_DEBT candidate**: parameterize settle time or poll /health 
  until ready.

- **No alembic / migration runner**: Production Neon migrations are applied 
  manually via `psql -f migrations/00X.sql`. Audit confirmed all migrations 002-005 
  applied to production through manual ops over the past months. Phase 1A scope: 
  add minimal `schema_versions(filename, applied_at)` table introspection, even 
  if we don't adopt alembic full-stack. Currently "what's applied" is inferred 
  from table presence — fine while migration count is low, fragile longer term.

- **fly secrets list doesn't show values**: Verifying `TEST_MODE` value required 
  indirect inference (server starts → not "true"). For future deploys: capture 
  exact secret values in a sealed retrospective note before deploy day, so 
  comparison is direct.
